Shadowsocks as a Transport — Implementation Plan

Two independent deliverables: (A) Shadowsocks as a WireGuard-carrying DPI-evasion transport in the daemon, and (B) Shadowsocks as a fallback path for the desktop app's hub control-plane traffic — used only after cached direct IP, direct domain and DoH-resolved IP have all failed.
Repos: pangeavpn-app (daemon + desktop) and PangeaHubServer (hub + node).

1. Current state & why this is cheap

Shadowsocks already exists across this stack — just never as a first-class desktop transport:

WhereWhat exists today

node/src/routes/ssAddUser.js /internal/ss-add-user / ss-remove-user, JWT-authed from the hub, sending add:/remove: commands to 127.0.0.1:6100 over UDP (node/src/services/ssManagerService.js). Method support comes from sing-shadowsocks2 v0.2.1, whose CreateMethod registry covers three families: shadowaead (aes-{128,192,256}-gcm, chacha20-ietf-poly1305, xchacha20-ietf-poly1305), shadowaead_2022 (2022-blake3-aes-{128,256}-gcm, 2022-blake3-chacha20-poly1305), and the legacy shadowstream ciphers. The options.go allow-list must admit the first two families and reject shadowstream — those ciphers are unauthenticated and trivially probed.

Module graph note. daemon/go.sum currently has no github.com/sagernet/sing-shadowsocks2 entry — Go's module graph pruning drops it because nothing in the build imports protocol/shadowsocks, which is the only thing that pulls it in. It is not a dependency we add by hand: it is sing-box's own, and the daemon never imports it directly. The first task of Phase 1 is simply to write the import "github.com/sagernet/sing-box/protocol/shadowsocks" in the new package and run go mod tidy inside daemon/; tidy then records sing-shadowsocks2 (plus its own transitive entries) as // indirect. Expect go.mod/go.sum churn only; nothing else in the tree changes.

2. Goals and non-goals

Goals

  • G1. A shadowsocks transport in the daemon that carries WireGuard UDP, shaped exactly like reality/hysteria2: loopback UDP listener → in-process sing-box outbound → node's WireGuard listener.
  • G2. A Shadowsocks path for the desktop's hub traffic (the /v1/secure envelope), engaged only after all three existing ensureHub() steps — cached IP, direct domain, DoH-resolved IP — have failed.
  • G3. Backup positioning: Shadowsocks never pre-empts Cloak for the tunnel, and never pre-empts cached IP / direct domain / DoH for the hub. It sits at the back of both cascades.
  • G4. Zero regression: every existing transport, the kill switch, and the Lockdown no-DNS invariant behave exactly as before when Shadowsocks is absent from a profile.

Non-goals (this plan)

  • Android/TV client support — apps/android has no transport wiring yet; out of scope.
  • Replacing the mobile Shadowrocket flow (ShadowsocksConfig table, /api/shadowrocket/*) — untouched.
  • SIP003 plugin chaining (external ck-client process). We reach Cloak in-process already; running SS through Cloak is explicitly rejected below.

3. Architecture

3.1 Deployment shape: direct SS, not SS-over-Cloak

Two options exist; only one is worth building as a transport:

OptionNode changeVerdict
SS through Cloak — SS outbound dials 127.0.0.1:<local cloak port> with ProxyMethod: shadowsocks. None. ProxyBook.shadowsocks already exists. Reject as a transport. If Cloak is blocked, this is blocked. It adds a second wire format behind an identical outer handshake — no censorship-resistance diversity, only overhead. (Still fine as a debug/lab mode.)
Direct SS — a second ssserver instance bound publicly on the node, client dials it straight. New listener + published port + ACL. Build this. A genuinely independent wire protocol and independent port/IP-level failure mode from Cloak, REALITY, Hysteria2 and NaiveProxy.

3.2 Data path (G1 — WireGuard over Shadowsocks)

WireGuard (userspace, daemon) │ peer Endpoint = 127.0.0.1:<boundLocalPort> ▼ shadowsocks.Manager ── loopback *net.UDPConn ──┐ │ bridgeUDP (single-flow NAT, │ identical to reality/bridge.go) ▼ sing-box Outbound(tag="shadowsocks-out").ListenPacket(ctx, 127.0.0.1:51820) │ SS AEAD UDP datagrams (or UoT when udpOverTcp=true) ▼ node: ssserver (public port, tcp_and_udp) │ relays to the destination in the SS header ▼ node: wg0 listener 127.0.0.1:51820

This mirrors daemon/internal/reality/manager.go almost line for line: single outbound, no local SOCKS inbound, ListenPacket against a fixed destination, a two-goroutine UDP bridge, and a generation counter guarding against a zombie bridge from a previous Start. Do not copy the hysteria2 shape (mixed inbound + SOCKS5 UDP ASSOCIATE) — that indirection exists only because sing-quic needs it.

Destination choice. Default targetPort = 51820 against 127.0.0.1, same convention as reality.defaultTargetPort (reality/manager.go:59, which hardcodes 127.0.0.1 and exposes only the port; Shadowsocks adds targetHost because its ACL makes the address a deployment variable). If a hardened ssserver ACL refuses loopback destinations, fall back to the node's WG interface address (10.10.1.1:51820).

Coupled to the node. targetHost is only "hub-configurable without a client release" as far as the node's outbound_allow_list permits — changing it means editing SS_RELAY_TARGET and restarting ssserver-public too. It buys a config change instead of a client release, not a config change instead of a deploy.

3.3 Data path (G2 — hub control plane over Shadowsocks)

Electron main (pangeaApiClient.hubFetch) │ POST /v1/secure {eph, iv, ct, tag} ← already end-to-end encrypted ▼ hubTransport.ts ── TCP → 127.0.0.1:<daemon SS proxy port> │ HTTP CONNECT <hubIp>:443 (mixed inbound speaks HTTP CONNECT) │ then tls.connect({ socket, servername: "" }) ← same no-SNI trick as fetchDohResolved ▼ daemon: shadowsocks.ProxyManager (mixed inbound → shadowsocks outbound, no WG bridge) ▼ node ssserver ──→ api.pangeavpn.org:443

The app never gains a SOCKS dependency: sing-box's mixed inbound already answers HTTP CONNECT, and Node's tls.connect({ socket }) + https.request({ createConnection }) composes over it with zero new npm packages. This also preserves the existing servername: "" / rejectUnauthorized: false behaviour that fetchDohResolved relies on.

Bootstrap chicken-and-egg. SS hub credentials normally come from the hub. On a cold install behind a block there is nothing cached. Resolution — two sources, tried in order:
  1. Cached SS entry persisted to settings.json from the last successful /api/client/regions (exactly how cachedHubIp already works).
  2. Baked-in bootstrap entry compiled into the app — host IP, port, method, password — rotatable via app update. Precedent already exists: SERVER_PUBLIC_KEY_B64 is pinned in secureChannel.ts. Point it at a dedicated control-plane SS listener whose ACL only permits the hub IP:443, so a leaked bootstrap password buys an attacker nothing but a path to our own public API.

4.1 Node: a publicly-bound ssserver

node/entrypoint.sh edit

Keep the existing loopback instance untouched (Cloak depends on it). Add a second config + ACL, and register its supervisord program the way every other opt-in service on this node does — by writing /etc/supervisor/conf.d/*.conf only when the env vars are set:

# ── Public Shadowsocks (direct transport) ──────────────────────────────
SS_PUBLIC_PORT="${SS_PUBLIC_PORT:-8488}"
if [ -n "$SS_PUBLIC_PASSWORD" ]; then
  cat > /etc/shadowsocks/config-public.json <<EOF
{
  "server": "0.0.0.0",
  "server_port": ${SS_PUBLIC_PORT},
  "password": "${SS_PUBLIC_PASSWORD}",
  "method": "${SS_PUBLIC_METHOD:-chacha20-ietf-poly1305}",
  "mode": "tcp_and_udp",
  "timeout": 300,
  "acl": "/etc/shadowsocks/public.acl",
  "security": { "replay_attack": { "policy": "reject" } }
}
EOF
  # ACL: this listener is a tunnel endpoint, NOT an open proxy. The OUTBOUND
  # sections are what enforce that — see the note below on why [white_list] is
  # the wrong tool here.
  cat > /etc/shadowsocks/public.acl <<EOF
[outbound_block_all]
[outbound_allow_list]
${SS_RELAY_TARGET:-127.0.0.1}
EOF
  cat > /etc/supervisor/conf.d/ss-public.conf <<EOF
[program:ssserver-public]
command=ssserver -c /etc/shadowsocks/config-public.json
autostart=true
autorestart=true
stdout_logfile=/dev/null
stdout_logfile_maxbytes=0
stderr_logfile=/dev/null
stderr_logfile_maxbytes=0
priority=12
EOF
  echo "[entrypoint] public Shadowsocks registered at /etc/supervisor/conf.d/ss-public.conf"
else
  rm -f /etc/supervisor/conf.d/ss-public.conf
  echo "[entrypoint] SS_PUBLIC_PASSWORD not set — public Shadowsocks is opt-in per node, skipping"
fi
The ACL is not optional, and the obvious sections are the wrong ones. fixed shadowsocks-rust gives ssserver two independent ACL axes, and only one of them restricts where the server will relay to:
SectionsWhat they actually filter
[reject_all] / [accept_all] + [white_list] / [black_list] The client's source address. Upstream wording: "[reject_all] — rejects all clients except those matching any rules", "[white_list] — rules for accepted clients".
[outbound_block_all] / [outbound_allow_all] + [outbound_allow_list] / [outbound_block_list] The destination the server relays to. This is the open-proxy control.
The earlier draft of this plan used [reject_all] + [white_list] 127.0.0.1, 10.10.1.1, HUB_IP. That would have rejected every real user (their source IPs are arbitrary and unknowable) while leaving the relay wide open to anyone who did get in — exactly backwards. Ship the outbound form above, in the same commit as the listener.
The outbound allow-list is address-scoped, not port-scoped. fixed Allowing 127.0.0.1 lets an authenticated SS client reach every loopback service on the node, not just WireGuard on 51820 — the node API (:3001), Cloak's admin client (:8100), sing-box's inbounds, and ssmanager (:6100) if Phase 4 ever starts it. Switching targetHost to 10.10.1.1 does not fix this: services bound to 0.0.0.0 answer on the WG address too. Mitigations, in order of preference:
  1. Run ssserver-public as a dedicated uid and add an iptables rule -A OUTPUT -m owner --uid-owner ssrelay ! --dport 51820 -j REJECT — the only mechanism that actually enforces the port.
  2. Bind the node API and admin services to interfaces the relay cannot reach.
  3. At minimum, treat the shared password as granting node-loopback access and prioritise Phase 4's per-device credentials accordingly.

// buildShadowsocksBlock returns the client-facing Shadowsocks connection block
// for a node, or undefined if the node has no shadowsocks config. Credentials
// are static per node (shared password) until per-device provisioning lands —
// same reasoning as buildHysteria2Block: a pure copy, no DB lookups.
export function buildShadowsocksBlock(node) {
  if (!node.shadowsocks) return undefined;

  const { remoteHost, remotePort, method, password,
          targetHost, targetPort, udpOverTcp } = node.shadowsocks;
  return {
    remoteHost,
    remotePort,
    method,
    password,
    // Hub-configurable so a node whose ssserver ACL refuses loopback can be
    // repointed at 10.10.1.1 without a client release (see §3.2).
    ...(targetHost ? { targetHost } : {}),
    ...(targetPort ? { targetPort } : {}),
    ...(udpOverTcp ? { udpOverTcp: true } : {}),
  };
}

func buildOutboundOptions(p state.ShadowsocksProfile) *option.ShadowsocksOutboundOptions {
    opts := &option.ShadowsocksOutboundOptions{
        ServerOptions: option.ServerOptions{
            Server:     p.RemoteHost,
            ServerPort: uint16(p.RemotePort),
        },
        Method:   methodOrDefault(p.Method),
        Password: p.Password,

    // adds framing overhead and a second fingerprintable layer for nothing.
    if p.UDPOverTCP {
        opts.UDPOverTCP = &option.UDPOverTCPOptions{Enabled: true}
    }
    return opts
}
Why no SessionWaiter. transport.SessionWaiter is optional and checked by type assertion. For Cloak/REALITY/Hysteria2 a successful handshake proves credentials; for Shadowsocks ListenPacket merely dials a UDP socket at the server and returns instantly even with a wrong password. Service.bringUpTransport's existing waitForWireGuardHandshake gate is the honest end-to-end proof and already runs for every transport. 6. Cascade & kill-switch integration

6.1 Auto-cascade position

// before
var autoCascadeOrder = []string{"cloak", "reality", "hysteria2", "naive", "snowflake"}
// after
var autoCascadeOrder = []string{"cloak", "reality", "hysteria2", "naive", "shadowsocks", "snowflake"}

Rationale, to be added as a sixth bullet in the existing comment block at lines 671–687: plain AEAD Shadowsocks is the most widely-fingerprinted protocol in the set — the GFW has active-probed and entropy-classified it for years. It earns its slot on independence (different port, different wire format, survives a Cloak- or QUIC-specific block) not on stealth, so it goes behind everything with a TLS-shaped or randomised handshake. reorderByMemory may still promote it to first on a network where it is the thing that worked — that path needs no change.

fixed "Second-to-last" is nominal only. snowflakeReleaseGated = true (service.go:618), so transportStarter returns false for snowflake and it never enters the candidate list. In every shipping build, Shadowsocks would be the actual last transport tried — the slot decision in §11 should be made on that basis, not on the nominal ordering.

11. Risks & open decisions

RiskAssessment / mitigation
Plain SS is well-fingerprinted. Real and unavoidable at the protocol level. The GFW active-probes AEAD SS and classifies it on packet entropy/length. This is why it sits second-to-last in the cascade and is framed as a diversity backup, not a stealth upgrade. Phase 4's SS-2022 (with replay_attack: reject, already in the config above) materially improves probe resistance.
Public SS listener = open proxy. Highest-severity item here. Mitigated by the shadowsocks-rust outbound ACL (§4.1), a non-default port, and Phase 4 per-device credentials. Do not ship the listener without the ACL — and check it is the outbound form: the client-side [reject_all]/[white_list] pair looks like it does this job and does the opposite.
Relay reaches all node loopback services. fixed shadowsocks-rust ACLs match addresses, not ports, so allowing the WireGuard target also allows the node API, Cloak admin, sing-box inbounds and (post-Phase 4) ssmanager on the same address. New risk, not present in the earlier draft. Enforce the port outside the ACL — dedicated uid + iptables owner rule (§4.1) — or accept that the shared password grants node-loopback reach and treat Phase 4 as a prerequisite rather than a nice-to-have.
Shared node password. One leak deanonymises nothing (traffic is WG-encrypted inside) but does grant tunnel access, plus the loopback reach above. Bounded by the ACL; properly fixed by Phase 4.
go.sum churn. New indirect dep sing-shadowsocks2, unpruned by the first protocol/shadowsocks import. Low risk — it is sing-box's own dependency at a version sing-box already pins — but re-run the full daemon test suite and confirm the Windows/macOS/Linux builds in .github after tidy.
Loopback destination refused by ssserver. Handled by making targetHost hub-configurable: switch to 10.10.1.1 without a client release.
MTU / fragmentation. Measure before shipping (§6.3). Do not lower the global default speculatively.
Baked-in bootstrap credential leaks. By design it reaches only hubIp:443 — our own public API. Rotate on app release. Precedent: the pinned SERVER_PUBLIC_KEY_B64.

Decisions to confirm before Phase 0

  1. Public SS port number — 8488 is a placeholder. Something that reads as a mundane service is better than an SS-adjacent number.
  2. Method for v1 — plan assumes chacha20-ietf-poly1305 (matches the node's existing config and the hub's SHADOWSOCKS_CIPHER constant). Going straight to 2022-blake3-aes-128-gcm is strictly better security-wise, but it is not free: the password becomes base64 key material of an exact length and the clock-skew requirement appears (see Phase 4). Deciding now still beats migrating later — just budget the key-generation work.
  3. Separate control-plane listener, or reuse the tunnel listener with a wider ACL? Plan assumes separate (tighter blast radius, independent rotation). Reuse is one fewer moving part.
  4. How does controlPlaneShadowsocks reach the client? /api/client/regions returns a bare array today, so a top-level object breaks existing clients. Per-region duplication is additive and safe; a new endpoint is cleaner. Needed before Phase 3.
  5. Cascade slot — plan puts shadowsocks 5th of 6 nominally, but with snowflakeReleaseGated that is last in every shipping build (§6.1). Confirm it should not sit ahead of naive.

Roughly: Phase 0 ≈ 1–2 days (the ACL and the loopback-scoping mitigation are the substance, not the listener), Phase 1 ≈ 2–3 days (the new package is a close structural copy of internal/reality), Phase 2 ≈ 1 day, Phase 3 ≈ 2–3 days (the CONNECT-proxy transport is the only genuinely new shape in the codebase). Phase 4 is independent and can trail a release, but grew an ssmanager prerequisite and real SS-2022 key handling — closer to 2 days than the "swap two config values" it read as before.
